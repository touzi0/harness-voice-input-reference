# prompt-injection —— 「用户用了语音输入 → 往环境提示词里加一句说明」的完整链路

这个目录是本项目**最关键的一块**：语音输入法识别出的文字不是简单地塞进输入框就完事，
它还要让后面的模型知道「这段人话是语音转写来的，可能有同音错字，请按上下文理解」。

这一段逻辑在产品里**跨了三个进程/两个仓库位置**，没有办法用一个文件表示，
所以这里按数据流顺序摘成 5 个片段文件（每个文件头部都写明原文路径、行号与原函数名）：

| 顺序 | 文件 | 原文位置 | 作用 |
|---|---|---|---|
| ① | `01-component-mark.js` | `组件/voice/client.js`（784-794、866-877、1782-1791） | 语音文字落进输入框时，在输入框上打 `data-jx-voice="1"` 标记 |
| ② | `02-send-report.js` | `web/app-chat.js`（5882-5888、5914-5917、5966-5970、6049-6051、6098-6101） | 发送时读标记，把 `voiceUsed: true` 随消息上报给后端，随即清标记 |
| ③ | `03-server-sticky-flag.go` | `server.go`（handleChat 3991-4008 / handleInterject 2996-3006）、`store.go`（迁移 327-336、MarkVoiceUsed 782-790、scanSession 809） | 收到 `voiceUsed` 就把会话的粘性标记置位（一次置位、永不撤下） |
| ④ | `04-env-prompt-inject.go` | `agent.go` 的 `envPrompt()`（686-688 是那一行，511-522 是函数头）、`maybeAppendEnvSnapshot()`（983-1014）、`kinds.go`（22） | 组装「运行环境快照」时，标记置位就多写一行说明；快照以 `role=system` 追加进上下文 |
| ⑤ | `05-voice-used_test.go` | `voice_used_test.go`（整文件） | 钉住上面这条行为的测试：未用过不出现、用过每轮都在、不串会话 |

一句话概括这条链：

```
用户按住热键说话
  → 识别出文字 → commitText() 写进输入框，同时 input.dataset.jxVoice = '1'
  → 用户按发送 → prepareSend() 读 dataset.jxVoice → POST /chat { voiceUsed: true }
  → 后端 handleChat() 见 voiceUsed → m.VoiceUsed = true + UPDATE sessions SET voice_used=1
  → 之后每一轮组装「运行环境快照」时，envPrompt() 里多出一行：
      "- 用户在本对话中使用过语音输入（听写转写）：消息可能混有同音错字，
        请按上下文理解其本意，在回复中自然使用正确写法，不必特意指出"
  → 这一行作为 role=system 的快照消息进上下文（模型第 0 轮就看得见）
```

## 三个容易踩的点（原实现为此付出的代价，都写进注释了）

1. **标记必须由"写输入框的那一处"打**：组件里写输入框正文只有 `commitText()` 一个入口，
   标记就打在那儿。散在多处打，迟早漏一处（拖进来的文件、粘贴、重新识别……）。
2. **标记必须有撤销时机**：发送清框时删（`delete input.dataset.jxVoice`），
   用户手动删光时也删（`input` 事件里判空）。否则「用过一次语音之后，
   后面纯打字的每条消息都被当成语音」——那行提示就会一直挂着糊弄模型。
3. **粘性标记 vs 时间窗**：原实现早期用的是「全局 5 分钟时间窗」（插件时代
   `adapter_dsh_speech.go`），窗口一过提示就消失，而用户的语音习惯是长期的；
   现在是**按会话、一次置位终身有效**，且快照逐字稳定（不闪变），
   因为环境快照是差分下发的——同一状态下每轮必须组装出**完全相同**的一行，
   否则每轮都会触发一次「环境更新」白烧 token（测试 ⑤ 就钉这一点）。

## 为什么不"直接纠正错字"，而是交给模型按上下文理解

这是这套做法最核心的判断，值得单独说清楚：

- **同音错字没有局部正确答案**。`识别 → 纠错` 这层如果自己改字，只能靠读音相似性猜，
  没有句子意图、没有对话历史、没有领域词汇表。用户说「把那个借口的报表发我」，
  到底是「接口」还是「借口」，只有上下文知道；猜错就是**改坏了原文**，
  而改坏比不改更糟——模型再读到的是一句被悄悄篡改过的话，没有任何信号提示它可疑。
- **一句话两处错，纠错层的置信度会互相拖累**。语音链路的错字常常是成串的
  （专有名词、人名、型号），纠错层要么全改要么全不改，很容易把一个本来对的词改错。
- **模型本来就更擅长这件事**。它能同时看到：这句转写、前面几轮对话、工作区里的文件、
  用户的历史偏好。同一个模型，给它「这是语音转写、可能有同音错字」这一句元信息，
  和让它面对一段被粗暴改写过的文本，前者的信息量严格更大。
- **错字保留 = 用户真实说过的话被保留**。转写是证据，纠错是解释。把两层分开，
  出问题时还能回查「用户到底说了什么」（本项目还留了最近三条原始音频，
  见主 README 的音频记录一节）。
- **成本**：一行 prompt ≈ 40 token，一次性、粘性、可缓存（前缀不变只差分）。
  为纠错专门跑一次模型调用，通常比分给它一个前缀更贵，且引入一次额外的失败点。

所以这里的分工是：**识别层负责"听清楚"，提示词层负责告诉模型"这段人话是听来的"。**
不让识别层假装自己听得懂上下文。
